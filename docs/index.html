Match Day Poll

Build and operate a small live-voting system on Kubernetes: replicas, scaling, releases, failures and security, driven by one evening of traffic.

The story

A cricket site runs a live poll: "Who wins tonight?" Before the match it is quiet. When the match starts, thousands of fans vote at once. The site has to stay up and scale. A new release will go wrong and has to be rolled back. A pod and a node will die. An auditor will ask who can reach what. And the database must never lose a vote.

You build the whole thing on a local Kubernetes cluster, one evening at a time. Each act is a problem from that story.

The frontend serves the poll page and forwards /api/* to the backend. The backend writes each vote to Postgres and keeps running totals in Redis. The frontend never talks to the database, and Act 6 makes the cluster enforce that.

No registry is used. You build the two images locally and load them straight into the cluster. Only the base images (Python, nginx, Postgres, Redis) are pulled from a public registry when you build or deploy.

How this guide works

The application code and the Dockerfiles are ready in app/. You write everything else: the cluster config, every Kubernetes manifest, and the load script. Put manifests in k8s/ and scripts in scripts/.

Each mission has a goal, the files you write, a check to run, and optional help. Try it yourself first, then open help only as needed:

  • Predict first (green): think about what will happen before you run the check.
  • Hint 1, Hint 2 (amber): a nudge, then a stronger nudge.
  • Full solution (blue): the working file. Compare it with yours after you finish.

The tick on each mission is saved in your browser only.

This guide assumes you already know Kubernetes basics. It explains what to do, not what a Deployment is.

Backend environment variables

VariableDefaultMeaning
DB_HOST, DB_PORT, DB_NAMEpostgres, 5432, pollWhere the database is
DB_USER, DB_PASSWORDpoll, (empty)Credentials. Come from the Secret
REDIS_HOSTredisWhere Redis is
CACHE_PORT6379Redis port. Leave unset
TEAMSIndia,AustraliaThe two options on the poll
CPU_COST_MS5Busy-work per vote, so load costs real CPU
NODE_NAMEunknownFill from the Downward API; the page shows which node answered
Why not REDIS_PORT? For every Service in a namespace, Kubernetes injects environment variables into the pods started after it, named after the Service. A Service called redis produces REDIS_PORT=tcp://10.96.x.x:6379 and REDIS_SERVICE_HOST, which would silently override an app setting of the same name. You can switch this off with enableServiceLinks: false in the pod spec.

Backend endpoints

EndpointMeaning
GET /healthLiveness. Never checks dependencies
GET /readyReadiness. Returns 503 until the database tables exist. Redis is optional
POST /voteBody {"team": "India"}
GET /resultsTotals. From Redis; rebuilt from Postgres when the cache is empty. Version 1.1 and later add percentages

Through the frontend these are /api/vote, /api/results and so on. The frontend also has GET /healthz.
