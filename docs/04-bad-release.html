Halftime

Act 4 · Bad release

A zero-downtime release, a release that never becomes ready, and the two ways back.

Story: at halftime the team ships a new feature (percentages on the poll). Then a second release goes out with a bug. Both happen with real fans voting, so neither may cause downtime.
4.1

Make releases safe

Configure the backend Deployment's update strategy: during an update, never drop below the desired number of ready pods, and add at most one extra pod. Keep five old versions for rollback, fail a stuck rollout after 60 seconds, and record a reason for each release.

You write: k8s/30-backend.yaml

Check

kubectl apply -f k8s/30-backend.yaml
kubectl get deploy backend -o jsonpath='{.spec.strategy}{"\n"}'

Expect: The strategy shows maxSurge: 1 and maxUnavailable: 0.

Hint 1
Fields: strategy.rollingUpdate.maxSurge, maxUnavailable, revisionHistoryLimit, progressDeadlineSeconds, and the annotation kubernetes.io/change-cause.
Full solution
metadata:
  name: backend
  namespace: poll
  labels: { app: backend }
  annotations:
    kubernetes.io/change-cause: "1.0 initial release"
spec:
  replicas: 3
  revisionHistoryLimit: 5
  progressDeadlineSeconds: 60
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
4.2

Ship version 1.1 without downtime

Build poll-backend:1.1, load it into the cluster, and roll it out by changing the image in your manifest. While it rolls, watch the status codes from a second terminal.

You write: k8s/30-backend.yaml

Check

docker build --build-arg APP_VERSION=1.1 -t poll-backend:1.1 app/backend
kind load docker-image poll-backend:1.1 --name poll
# terminal 2:
while true; do curl -s -o /dev/null -w '%{http_code}\n' localhost:8080/api/results; sleep 0.2; done | uniq -c
# terminal 1: change the image to poll-backend:1.1 (and the change-cause), then
kubectl apply -f k8s/30-backend.yaml
kubectl rollout status deploy/backend

Expect: Terminal 2 shows only 200: no failed request during the rollout. The page now shows percentages and backend v1.1.

Predict first: how many backend pods exist at the busiest moment of the rollout?
Four: 3 desired plus 1 surge. With maxUnavailable: 0 an old pod is removed only after a new one is Ready.
Hint 1
Edit the image: line and apply the file. Avoid kubectl set image: it changes the cluster but not your manifest, and your file is the record of what runs.
4.3

Ship a broken version

Build poll-backend:1.2-broken with the build arguments from the Dockerfile's comment, load it, and roll it out. It starts but never becomes ready.

Check

docker build --build-arg APP_VERSION=1.2 --build-arg BROKEN=true -t poll-backend:1.2-broken app/backend
kind load docker-image poll-backend:1.2-broken --name poll
# change the image to poll-backend:1.2-broken, then
kubectl apply -f k8s/30-backend.yaml
kubectl rollout status deploy/backend --timeout=75s
kubectl get pods -l app=backend
kubectl get deploy backend

Expect: The rollout does not finish: progress deadline exceeded. One new pod sits at 0/1 while the three good pods keep serving. Terminal 2 from the previous mission would still show only 200.

Predict first: how many pods are Running, and which version answers requests?
Four Running (one of them not Ready): the three 1.1 pods answer. The new pod is never added to the Service because its readiness check fails.
4.4

Roll back

Return to the last good version and check what Kubernetes remembers.

Check

kubectl rollout history deploy/backend
kubectl rollout undo deploy/backend
kubectl rollout status deploy/backend
curl -s localhost:8080/api/version

Expect: History lists several revisions. After the undo, the version shown is 1.1 again.

Predict first: what happens if you now run kubectl apply -f k8s/30-backend.yaml again?
It redeploys the broken image, because your file still names it. rollout undo changes the cluster, not your manifest. Set the file back to poll-backend:1.1.
Hint 1
Fix the file first, then apply it: that is the declarative way to roll back. undo is the quick emergency lever.
4.5

Protect against voluntary disruption

Add PodDisruptionBudgets: at least 2 backend pods and at least 1 frontend pod must stay available during voluntary disruptions such as node drains.

You write: k8s/80-pdb.yaml

Values to use

PodDisruptionBudgetSelectorMinimum available
backendapp: backend2
frontendapp: frontend1

Check

kubectl apply -f k8s/80-pdb.yaml
kubectl get pdb

Expect: ALLOWED DISRUPTIONS is the replica count minus the minimum (for example 3 backends, minimum 2: allowed 1). You will use this in Act 5.

Full solution
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: backend
  namespace: poll
spec:
  minAvailable: 2
  selector:
    matchLabels: { app: backend }
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: frontend
  namespace: poll
spec:
  minAvailable: 1
  selector:
    matchLabels: { app: frontend }
4.6

Checkpoint: compare your backend manifest

Open this only when you are done with this act. It is the complete backend manifest as it should look now, with everything from Acts 1 to 4. Differences are fine as long as the behaviour matches.

Full solution
apiVersion: v1
kind: Service
metadata:
  name: backend
  namespace: poll
  labels: { app: backend }
spec:
  selector: { app: backend }
  ports:
    - { name: http, port: 8000, targetPort: http }
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend
  namespace: poll
  labels: { app: backend }
  annotations:
    kubernetes.io/change-cause: "1.1 adds percentages"
spec:
  replicas: 3
  revisionHistoryLimit: 5
  progressDeadlineSeconds: 60
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels: { app: backend }
  template:
    metadata:
      labels: { app: backend }
    spec:
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: ScheduleAnyway
          labelSelector:
            matchLabels: { app: backend }
      containers:
        - name: backend
          image: poll-backend:1.1
          ports:
            - { name: http, containerPort: 8000 }
          envFrom:
            - configMapRef: { name: poll-config }
          env:
            - { name: DB_USER, valueFrom: { secretKeyRef: { name: db-credentials, key: username } } }
            - { name: DB_PASSWORD, valueFrom: { secretKeyRef: { name: db-credentials, key: password } } }
            - { name: NODE_NAME, valueFrom: { fieldRef: { fieldPath: spec.nodeName } } }
          readinessProbe:
            httpGet: { path: /ready, port: http }
            periodSeconds: 5
            failureThreshold: 2
          livenessProbe:
            httpGet: { path: /health, port: http }
            initialDelaySeconds: 5
            periodSeconds: 10
          resources:
            requests: { cpu: 100m, memory: 128Mi }
            limits: { memory: 256Mi }
