Act 7 · Housekeeping

A reset Job, a scheduled snapshot, and a script that rebuilds the whole system from your files.

Story: match over. Prepare for the next one: clear the poll with a one-off Job, take a snapshot of the totals every few minutes with a CronJob, and prove you can rebuild the whole system from your files with one command.
7.1

Reset the poll with a Job

Write a Job that runs python tools.py reset in the backend image. It deletes all votes and clears the Redis cache. Its pod label must be app: backend-job so your network policies allow it to reach the database and Redis.

You write: k8s/95-reset-job.yaml

Values to use

SettingValue
Imagepoll-backend:1.1 (or the tag you run)
Command["python", "tools.py", "reset"]
EnvDB_HOST, DB_PORT, DB_NAME, REDIS_HOST from the ConfigMap; DB_USER, DB_PASSWORD from the Secret
Pod labelapp: backend-job

Check

curl -s localhost:8080/api/results
kubectl apply -f k8s/95-reset-job.yaml
kubectl wait --for=condition=complete job/poll-reset --timeout=90s
kubectl logs job/poll-reset
curl -s localhost:8080/api/results

Expect: The log says reset: votes deleted, cache cleared, and the totals are 0.

Predict first: what happens if you apply the same Job file a second time?
Nothing runs: a finished Job is not run again by apply, and its pod template is immutable. Delete the Job first (kubectl delete job poll-reset), then apply it again.
Full solution
apiVersion: batch/v1
kind: Job
metadata:
  name: poll-reset
  namespace: poll
spec:
  backoffLimit: 2
  ttlSecondsAfterFinished: 3600
  template:
    metadata:
      labels: { app: backend-job }
    spec:
      restartPolicy: OnFailure
      containers:
        - name: reset
          image: poll-backend:1.1
          command: ["python", "tools.py", "reset"]
          envFrom:
            - configMapRef: { name: poll-config }
          env:
            - { name: DB_USER, valueFrom: { secretKeyRef: { name: db-credentials, key: username } } }
            - { name: DB_PASSWORD, valueFrom: { secretKeyRef: { name: db-credentials, key: password } } }
7.2

A nightly snapshot with a CronJob

Write a CronJob that runs python tools.py snapshot on a schedule. For this exercise run it every 2 minutes. Never allow two runs at once, and keep only the last two successful and the last failed Job.

You write: k8s/96-cronjob.yaml

Values to use

SettingValue
Namesnapshot
Schedule*/2 * * * * (every 2 minutes, for this exercise)
PoliciesconcurrencyPolicy: Forbid, keep 2 successful and 1 failed Job
Command["python", "tools.py", "snapshot"], image poll-backend:1.1
Env and labelsame as the reset Job; pod label app: backend-job inside the jobTemplate

Check

kubectl apply -f k8s/96-cronjob.yaml
# vote a few times, then wait about 4 minutes
kubectl get cronjob,jobs
kubectl logs job/$(kubectl get jobs -o name | tail -1 | cut -d/ -f2)
kubectl exec postgres-0 -- psql -U poll -d poll -c 'SELECT id, taken_at, total FROM snapshots'
kubectl patch cronjob snapshot -p '{"spec":{"suspend":true}}'

Expect: Jobs named snapshot-<number> appear every two minutes, only the last few are kept, the log shows snapshot: total=…, and the snapshots table fills up. After the suspend patch, no new Job appears.

Hint 1
Fields to set: schedule, concurrencyPolicy: Forbid, successfulJobsHistoryLimit, failedJobsHistoryLimit, and a jobTemplate that looks like the reset Job.
Hint 2
Remember the pod label app: backend-job inside the jobTemplate, not on the CronJob itself.
Full solution
apiVersion: batch/v1
kind: CronJob
metadata:
  name: snapshot
  namespace: poll
spec:
  schedule: "*/2 * * * *"
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 2
  failedJobsHistoryLimit: 1
  jobTemplate:
    spec:
      backoffLimit: 2
      template:
        metadata:
          labels: { app: backend-job }
        spec:
          restartPolicy: OnFailure
          containers:
            - name: snapshot
              image: poll-backend:1.1
              command: ["python", "tools.py", "snapshot"]
              envFrom:
                - configMapRef: { name: poll-config }
              env:
                - { name: DB_USER, valueFrom: { secretKeyRef: { name: db-credentials, key: username } } }
                - { name: DB_PASSWORD, valueFrom: { secretKeyRef: { name: db-credentials, key: password } } }
7.3

Rebuild everything with one command

Write scripts/up.sh, which creates the cluster, builds and loads the images, installs the add-ons, and applies your manifests in the right order. Write scripts/down.sh, which deletes the cluster. Then prove it: delete the cluster, run up.sh, and open the poll.

You write: scripts/up.sh, scripts/down.sh

Check

chmod +x scripts/*.sh
scripts/down.sh
scripts/up.sh
curl -s localhost:8080/api/results
kubectl get pods,hpa,pdb,networkpolicy,cronjob -n poll

Expect: From nothing, the poll answers at http://localhost:8080. Pods are Ready, and the HPA, PDBs, network policies and CronJob exist.

Predict first: what order must things be created in, and which step can fail if you get it wrong?
Namespace and config first, then the database, then the migration Job, then the backend and frontend, then the ingress, policies and the rest. The frontend crashes at start if the backend Service is missing, and the backend is never ready until the migration Job has run.
Hint 1
kubectl wait and kubectl rollout status let the script pause until a step is done. Add set -euo pipefail at the top so it stops at the first error.
Hint 2
The images up.sh builds must match the tags in your manifests. After Act 4 that is poll-backend:1.1, so change the migration Job's image to 1.1 too.
Full solution
#!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "$0")/.."

kind create cluster --config cluster/kind-cluster.yaml

docker build --build-arg APP_VERSION=1.1 -t poll-backend:1.1 app/backend
docker build -t poll-frontend:1.0 app/frontend
kind load docker-image poll-backend:1.1 poll-frontend:1.0 --name poll

kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.11.2/deploy/static/provider/kind/deploy.yaml
kubectl wait --namespace ingress-nginx --for=condition=ready pod \
  --selector=app.kubernetes.io/component=controller --timeout=180s
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/download/v0.7.2/components.yaml
kubectl patch -n kube-system deployment metrics-server --type=json \
  -p '[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'

kubectl apply -f k8s/00-namespace.yaml -f k8s/01-config.yaml
kubectl apply -f k8s/10-postgres.yaml -f k8s/20-redis.yaml
kubectl rollout status statefulset/postgres -n poll --timeout=180s
kubectl apply -f k8s/40-migrate-job.yaml
kubectl wait --for=condition=complete job/db-migrate -n poll --timeout=120s
kubectl apply -f k8s/30-backend.yaml -f k8s/50-frontend.yaml
kubectl rollout status deploy/backend -n poll --timeout=180s
kubectl rollout status deploy/frontend -n poll --timeout=180s
kubectl apply -f k8s/60-ingress.yaml -f k8s/70-hpa.yaml -f k8s/80-pdb.yaml
kubectl apply -f k8s/90-netpol.yaml -f k8s/91-rbac.yaml -f k8s/96-cronjob.yaml

echo "Ready: http://localhost:8080"
#!/usr/bin/env bash
kind delete cluster --name poll
