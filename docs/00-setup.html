Before the story starts

Act 0 · Setup

Images built, a three-node cluster running, and the add-ons installed. Nothing of the poll exists yet.

Run all commands from the repository root unless a mission says otherwise.
0.1

Install the tools

You need Docker (runs the cluster), kind (creates the cluster) and kubectl (talks to it). If kind says command not found, it is not installed or not on your PATH. This mission fixes both. Skip any tool you already have.

PATH in one sentence: when you type kind, your shell looks for a file called kind in each folder listed in the PATH variable. Installing a tool means putting its file in one of those folders, or adding its folder to the list.
Windows

Docker: install Docker Desktop, start it, and wait until it says it is running. It needs WSL 2, which the installer offers to set up.

kind and kubectl, option A: winget (one command each)

winget install -e --id Kubernetes.kind
winget install -e --id Kubernetes.kubectl

If winget cannot find a package, use option B.

Option B: download and set the PATH yourself

# 1. a folder for the tools, and add it to your user PATH (run this once)
New-Item -ItemType Directory -Force C:\Tools | Out-Null
[Environment]::SetEnvironmentVariable("Path", [Environment]::GetEnvironmentVariable("Path","User") + ";C:\Tools", "User")

# 2. download kind (pinned version; the kind Quick Start page lists newer ones)
curl.exe -Lo C:\Tools\kind.exe https://kind.sigs.k8s.io/dl/v0.33.0/kind-windows-amd64

# 3. download kubectl (the current stable release)
$v = (curl.exe -Ls https://dl.k8s.io/release/stable.txt)
curl.exe -Lo C:\Tools\kubectl.exe "https://dl.k8s.io/release/$v/bin/windows/amd64/kubectl.exe"

Then: open a new terminal

A changed PATH is only seen by terminals opened afterwards. Close every PowerShell and Git Bash window and open a new one.

# Git Bash reads the Windows PATH when it starts, so open a NEW Git Bash window.
# If a tool is still not found, add its folder for Git Bash only:
echo 'export PATH="$PATH:/c/Tools"' >> ~/.bashrc
source ~/.bashrc
macOS

Docker: install Docker Desktop and start it.

brew install kind kubectl
Linux
# kind (use kind-linux-arm64 on an ARM machine)
curl -Lo ./kind https://kind.sigs.k8s.io/dl/v0.33.0/kind-linux-amd64
chmod +x ./kind
sudo mv ./kind /usr/local/bin/kind

# kubectl
curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
sudo install -o root -g root -m 0755 kubectl /usr/local/bin/kubectl

# Docker Engine: follow docs.docker.com for your distribution, then
sudo usermod -aG docker $USER      # log out and in again afterwards

Check that your shell can find them

docker version --format '{{.Server.Version}}'
kind version
kubectl version --client
which kind kubectl      # Git Bash, macOS, Linux   (PowerShell: Get-Command kind, kubectl)

Expect: a Docker server version, a kind version (for example kind v0.33.0 go1.x ...), a kubectl client version, and a file path for each tool from which.

Hint 1: kind: command not found
The folder holding kind is not on your PATH, or the terminal was opened before you changed it. Open a new terminal. If it still fails, run which kind (Git Bash) or Get-Command kind (PowerShell): no output means the file is not on the PATH.
Hint 2: an older kubectl is found first
Docker Desktop installs its own kubectl. If kubectl version --client shows an old version, put your tools folder before Docker's in the PATH, or remove Docker's copy. A kubectl more than one minor version away from the cluster can behave oddly.
Hint 3: Docker errors
Cannot connect to the Docker daemon (or a pipe error on Windows) means Docker Desktop is not running yet. Start it and wait for the whale icon to settle.
0.2

Check your tools

Run one last check that all three tools answer in the shell you will work in.

Check

docker version --format '{{.Server.Version}}'
kind version
kubectl version --client

Expect: Three version outputs, no errors. If Docker fails, start Docker Desktop (or the Docker service).

0.3

Build the images

Build the backend and frontend images from the Dockerfiles in app/.

Check

docker build -t poll-backend:1.0 app/backend
docker build -t poll-frontend:1.0 app/frontend
docker images | grep poll
docker run --rm poll-backend:1.0 python -c "import main; print(main.VERSION)"

Expect: Two images listed, and the last command prints 1.0.

Hint 1
The Dockerfile has the exact docker build command in its first comment lines.
Hint 2
The backend image starts even without a database. It connects only when a request needs it.
0.4

Create the cluster

Write a kind config for a cluster named poll with one control-plane and two workers. Publish the ingress controller's port 80 on your machine's port 8080.

You write: cluster/kind-cluster.yaml

Check

kind create cluster --config cluster/kind-cluster.yaml
kubectl get nodes
kubectl config current-context

Expect: Three nodes Ready (poll-control-plane, poll-worker, poll-worker2) and context kind-poll.

Predict first: which node can run the ingress controller?
Only a node that is both labelled for it and reachable on host port 8080. The control-plane node carries the port mapping, so it also needs a label the controller selects on.
Hint 1
Look at the kind docs for extraPortMappings (containerPort 80, hostPort 8080) and kubeadmConfigPatches with node-labels.
Hint 2
The ingress controller manifest for kind selects nodes with the label ingress-ready=true. Put the mapping and the label on the control-plane node only.
Full solution
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: poll
nodes:
  - role: control-plane
    kubeadmConfigPatches:
      - |
        kind: InitConfiguration
        nodeRegistration:
          kubeletExtraArgs:
            node-labels: "ingress-ready=true"
    extraPortMappings:
      - containerPort: 80
        hostPort: 8080
        protocol: TCP
  - role: worker
  - role: worker
0.5

Load the images into the cluster

The cluster cannot see images in your local Docker. Copy them into every node. There is no registry.

Check

kind load docker-image poll-backend:1.0 poll-frontend:1.0 --name poll
docker exec poll-worker crictl images | grep poll

Expect: Both images listed on the worker node.

Hint 1
Whenever you build a new tag, load it again. A pod with ImagePullBackOff on a local image almost always means this step was skipped.
0.6

Add the ingress controller and metrics

Install two cluster add-ons: the NGINX ingress controller (for the 8080 URL) and metrics-server (needed for autoscaling and kubectl top). These are commands, not files you write.

Check

kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.11.2/deploy/static/provider/kind/deploy.yaml
kubectl wait --namespace ingress-nginx --for=condition=ready pod --selector=app.kubernetes.io/component=controller --timeout=180s

kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/download/v0.7.2/components.yaml
kubectl patch -n kube-system deployment metrics-server --type=json -p '[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'
kubectl top nodes

Expect: The controller pod becomes Ready. After a minute kubectl top nodes prints CPU and memory per node.

Hint 1
The --kubelet-insecure-tls patch is needed because kind nodes use self-signed kubelet certificates. Do not use it in production.
Hint 2
If kubectl top says metrics are not available yet, wait 60 seconds and retry.
