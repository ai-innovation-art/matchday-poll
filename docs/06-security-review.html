After the match

Act 6 · Security review

Network policies, a least-privilege identity, and containers locked down. Each change comes with a command that proves it.

Story: after the match an auditor reviews the setup and asks four questions. Who can reach the database? Who can read the cluster? What can the containers do on the node? And what proves it?
6.1

Prove the problem first

Right now every pod can talk to every other pod. Show that the frontend can open a connection to the database.

Check

kubectl exec deploy/frontend -- wget -T 3 -qO- http://postgres:5432

Expect: It returns within a second with a protocol error such as error getting response. That error proves the connection was accepted: the frontend can reach the database. Remember this result, you will compare it.

6.2

Only the right pods may talk

Write network policies so that: nothing is allowed in by default; only the ingress controller may reach the frontend (port 8080); only the frontend may reach the backend (8000); only the backend and backend Jobs may reach Redis (6379) and Postgres (5432).

You write: k8s/90-netpol.yaml

Check

kubectl apply -f k8s/90-netpol.yaml
kubectl exec deploy/frontend -- wget -T 3 -qO- http://postgres:5432
kubectl get pods
curl -s localhost:8080/api/results
curl -s -X POST -H 'Content-Type: application/json' -d '{"team":"India"}' localhost:8080/api/vote
kubectl run tmp --rm -it --image=busybox:1.36 --restart=Never -- wget -T 3 -qO- http://backend:8000/health

Expect: The frontend-to-database command now waits three seconds and ends with download timed out. All pods stay Ready. The site and voting still work through the Ingress. The throwaway pod, which has no allowed label, times out too.

Predict first: which policy makes the unlabeled throwaway pod fail?
The default-deny policy selects every pod, so a pod is reachable only if another policy allows the source. The backend's allow rule accepts only pods labelled app: frontend.
Hint 1
Start with a policy whose podSelector is empty and that lists only policyTypes: [Ingress] with no rules. Then add one allow policy per target.
Hint 2
The ingress controller lives in another namespace: use a namespaceSelector on kubernetes.io/metadata.name: ingress-nginx. For Redis and Postgres, match app with matchExpressions and operator In for the values backend and backend-job.
Hint 3
If pods go NotReady after applying the policies, see the Troubleshooting page.
Full solution
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: poll
spec:
  podSelector: {}
  policyTypes: [Ingress]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-ingress-controller-to-frontend
  namespace: poll
spec:
  podSelector:
    matchLabels: { app: frontend }
  policyTypes: [Ingress]
  ingress:
    - from:
        - namespaceSelector:
            matchLabels: { kubernetes.io/metadata.name: ingress-nginx }
      ports:
        - { protocol: TCP, port: 8080 }
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-backend
  namespace: poll
spec:
  podSelector:
    matchLabels: { app: backend }
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels: { app: frontend }
      ports:
        - { protocol: TCP, port: 8000 }
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-backend-to-redis
  namespace: poll
spec:
  podSelector:
    matchLabels: { app: redis }
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchExpressions:
              - { key: app, operator: In, values: [backend, backend-job] }
      ports:
        - { protocol: TCP, port: 6379 }
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-backend-to-postgres
  namespace: poll
spec:
  podSelector:
    matchLabels: { app: postgres }
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchExpressions:
              - { key: app, operator: In, values: [backend, backend-job] }
      ports:
        - { protocol: TCP, port: 5432 }
6.3

A read-only identity for the support team

Create a ServiceAccount poll-viewer that can read pods, their logs, services, endpoints, ConfigMaps, volume claims, workloads and Jobs in the poll namespace, and nothing else. It must not be able to read Secrets. Also create a ServiceAccount backend that does not mount an API token.

You write: k8s/91-rbac.yaml

Check

kubectl apply -f k8s/91-rbac.yaml
SA=system:serviceaccount:poll:poll-viewer
kubectl auth can-i list pods --as=$SA
kubectl auth can-i get pods/log --as=$SA
kubectl auth can-i delete pods --as=$SA
kubectl auth can-i get secrets --as=$SA
kubectl auth can-i list pods -n kube-system --as=$SA

Expect: yes, yes, no, no, no.

Predict first: why is the last answer no even though the first is yes?
A Role only grants access inside its own namespace. Access to kube-system would need a binding there, or a ClusterRole.
Hint 1
You need four objects: two ServiceAccounts, a Role and a RoleBinding. Set automountServiceAccountToken: false on the backend ServiceAccount.
Hint 2
Rules are grouped by API group: the core group is "", Deployments and StatefulSets are in apps, Jobs in batch. Use verbs get, list, watch only.
Full solution
apiVersion: v1
kind: ServiceAccount
metadata:
  name: poll-viewer
  namespace: poll
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: backend
  namespace: poll
automountServiceAccountToken: false
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: viewer
  namespace: poll
rules:
  - apiGroups: [""]
    resources: ["pods", "pods/log", "services", "endpoints", "configmaps", "persistentvolumeclaims"]
    verbs: ["get", "list", "watch"]
  - apiGroups: ["apps"]
    resources: ["deployments", "replicasets", "statefulsets"]
    verbs: ["get", "list", "watch"]
  - apiGroups: ["batch"]
    resources: ["jobs", "cronjobs"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: viewer
  namespace: poll
subjects:
  - kind: ServiceAccount
    name: poll-viewer
    namespace: poll
roleRef:
  kind: Role
  name: viewer
  apiGroup: rbac.authorization.k8s.io
6.4

Containers that cannot do much

Make the backend and frontend run as non-root with a read-only filesystem and no extra Linux capabilities. The backend should use the backend ServiceAccount. Give each a writable /tmp from an emptyDir.

You write: k8s/30-backend.yaml, k8s/50-frontend.yaml

Check

kubectl apply -f k8s/
kubectl rollout status deploy/backend
kubectl rollout status deploy/frontend
kubectl exec deploy/backend -- id
kubectl exec deploy/backend -- touch /app/x
kubectl exec deploy/backend -- touch /tmp/x
kubectl exec deploy/backend -- ls /var/run/secrets/kubernetes.io/serviceaccount
kubectl get pods

Expect: uid=10001; the write to /app fails with Read-only file system; the write to /tmp works; the last ls says No such file or directory (no API token); all pods Ready.

Predict first: what would break if you removed the emptyDir for the frontend?
nginx writes its pid file and temporary files under /tmp. With a read-only root filesystem and no writable /tmp it fails to start.
Hint 1
Pod-level securityContext: runAsNonRoot: true and a seccompProfile of RuntimeDefault. Container-level: allowPrivilegeEscalation: false, readOnlyRootFilesystem: true, capabilities.drop: [ALL].
Hint 2
Both images already declare a numeric non-root user, which is what runAsNonRoot checks.
Full solution
    spec:
      serviceAccountName: backend
      securityContext:
        runAsNonRoot: true
        seccompProfile: { type: RuntimeDefault }
      containers:
        - name: backend
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities: { drop: ["ALL"] }
          volumeMounts:
            - { name: tmp, mountPath: /tmp }
      volumes:
        - { name: tmp, emptyDir: {} }
    spec:
      securityContext:
        runAsNonRoot: true
        seccompProfile: { type: RuntimeDefault }
      containers:
        - name: frontend
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities: { drop: ["ALL"] }
          volumeMounts:
            - { name: tmp, mountPath: /tmp }
      volumes:
        - { name: tmp, emptyDir: {} }
6.5

Stretch: ask the cluster which workloads are not hardened

Label the namespace so Kubernetes warns about pods that violate the restricted pod security standard, then see which of your workloads fail it.

Check

kubectl label namespace poll pod-security.kubernetes.io/warn=restricted --overwrite
kubectl apply -f k8s/10-postgres.yaml -f k8s/20-redis.yaml

Expect: Warnings naming Postgres and Redis for missing settings such as allowPrivilegeEscalation, capabilities, runAsNonRoot and a seccomp profile. Backend and frontend, which you hardened in the last mission, produce none. Fixing the two official images is the stretch: both need a specific user and a writable data folder.

Hint 1
warn only prints a warning. enforce would reject the pods, and audit would record them in the audit log. Try enforce=baseline as a gentler next step.
