1.2

Secret and configuration

Create the Secret and ConfigMap with the names and keys from the start page. Credentials go in the Secret, everything else in the ConfigMap.

You write: k8s/01-config.yaml

Check

kubectl apply -f k8s/01-config.yaml
kubectl get secret,configmap
kubectl get configmap poll-config -o jsonpath='{.data}'

Expect: Secret db-credentials and ConfigMap poll-config exist. The ConfigMap shows six keys.

Hint 1
stringData lets you write the Secret values as plain text; the API server stores them base64-encoded.
Hint 2
Database host is postgres, Redis host is redis. Numbers in a ConfigMap must be quoted strings.
Full solution
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
  namespace: poll
type: Opaque
stringData:
  username: poll
  password: change-me-please
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: poll-config
  namespace: poll
data:
  DB_HOST: postgres
  DB_PORT: "5432"
  DB_NAME: poll
  REDIS_HOST: redis
  TEAMS: "India,Australia"
  CPU_COST_MS: "5"
1.3

The database

Run Postgres as a StatefulSet with a headless Service named postgres and a 500 Mi volume per replica. Take the database name, user and password from the ConfigMap and Secret.

You write: k8s/10-postgres.yaml

Check

kubectl apply -f k8s/10-postgres.yaml
kubectl get pods,pvc
kubectl exec postgres-0 -- psql -U poll -d poll -c '\conninfo'

Expect: postgres-0 is Running and PVC data-postgres-0 is Bound. \conninfo shows you are connected to database poll as user poll.

Predict first: why does the PVC stay Pending for a few seconds first?
kind's default StorageClass binds volumes only when a pod that uses them is scheduled, so the volume is created on the node the pod lands on.
Hint 1
The Postgres image reads POSTGRES_DB, POSTGRES_USER and POSTGRES_PASSWORD. Use valueFrom with configMapKeyRef / secretKeyRef.
Hint 2
Mount the volume at /var/lib/postgresql/data and set PGDATA to a sub-folder of it. A fresh volume has a lost+found folder that makes Postgres refuse to initialise in the mount root.
Hint 3
The volume comes from volumeClaimTemplates, not a separate PVC file. serviceName must match the headless Service.
Full solution
apiVersion: v1
kind: Service
metadata:
  name: postgres
  namespace: poll
  labels: { app: postgres }
spec:
  clusterIP: None
  selector: { app: postgres }
  ports:
    - { name: pg, port: 5432 }
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
  namespace: poll
  labels: { app: postgres }
spec:
  serviceName: postgres
  replicas: 1
  selector:
    matchLabels: { app: postgres }
  template:
    metadata:
      labels: { app: postgres }
    spec:
      containers:
        - name: postgres
          image: postgres:16-alpine
          ports:
            - { name: pg, containerPort: 5432 }
          env:
            - { name: POSTGRES_DB, valueFrom: { configMapKeyRef: { name: poll-config, key: DB_NAME } } }
            - { name: POSTGRES_USER, valueFrom: { secretKeyRef: { name: db-credentials, key: username } } }
            - { name: POSTGRES_PASSWORD, valueFrom: { secretKeyRef: { name: db-credentials, key: password } } }
            - { name: PGDATA, value: /var/lib/postgresql/data/pgdata }
          volumeMounts:
            - { name: data, mountPath: /var/lib/postgresql/data }
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: [ReadWriteOnce]
        resources:
          requests:
            storage: 500Mi

The cache

Run Redis as a single-replica Deployment with a Service named redis.

You write: k8s/20-redis.yaml

Check

kubectl apply -f k8s/20-redis.yaml
kubectl get pods -l app=redis
kubectl exec deploy/redis -- redis-cli ping

Expect: The pod is Running and redis-cli ping answers PONG.

Full solution
apiVersion: v1
kind: Service
metadata:
  name: redis
  namespace: poll
  labels: { app: redis }
spec:
  selector: { app: redis }
  ports:
    - { name: redis, port: 6379, targetPort: 6379 }
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: redis
  namespace: poll
  labels: { app: redis }
spec:
  replicas: 1
  selector:
    matchLabels: { app: redis }
  template:
    metadata:
      labels: { app: redis }
    spec:
      containers:
        - name: redis
          image: redis:7-alpine
          ports:
            - { containerPort: 6379 }
1.5

The backend, three replicas

Run the backend as a Deployment with 3 replicas and a Service named backend on port 8000. Give it every environment variable from the start page. Do not add probes yet.

You write: k8s/30-backend.yaml

Check

kubectl apply -f k8s/30-backend.yaml
kubectl get pods -l app=backend -o wide
kubectl port-forward svc/backend 8000:8000 &
sleep 2; curl -s -i localhost:8000/ready; kill %1

Expect: Three pods Running, spread over the worker nodes. /ready answers 503 with "waiting_for":["database"], because the tables do not exist yet. Without probes, Kubernetes does not know and the pods look healthy.

Predict first: what does a vote return right now?
A 503 database unavailable. The database is up, but the votes table is missing. The next mission creates it.
Hint 1
Use envFrom with the ConfigMap for the shared settings. Add DB_USER and DB_PASSWORD from the Secret, and NODE_NAME from fieldRef: spec.nodeName.
Hint 2
Name the container port http so the Service can refer to it by name.
Full solution
apiVersion: v1
kind: Service
metadata:
  name: backend
  namespace: poll
  labels: { app: backend }
spec:
  selector: { app: backend }
  ports:
    - { name: http, port: 8000, targetPort: http }
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend
  namespace: poll
  labels: { app: backend }
spec:
  replicas: 3
  selector:
    matchLabels: { app: backend }
  template:
    metadata:
      labels: { app: backend }
    spec:
      containers:
        - name: backend
          image: poll-backend:1.0
          ports:
            - { name: http, containerPort: 8000 }
          envFrom:
            - configMapRef: { name: poll-config }
          env:
            - { name: DB_USER, valueFrom: { secretKeyRef: { name: db-credentials, key: username } } }
            - { name: DB_PASSWORD, valueFrom: { secretKeyRef: { name: db-credentials, key: password } } }
            - { name: NODE_NAME, valueFrom: { fieldRef: { fieldPath: spec.nodeName } } }
1.6

Create the tables with a Job

Run python tools.py migrate in the backend image as a one-off Job. Give its pod the label app: backend-job (not backend, or the Service would send traffic to it).

You write: k8s/40-migrate-job.yaml

Check

kubectl apply -f k8s/40-migrate-job.yaml
kubectl wait --for=condition=complete job/db-migrate --timeout=90s
kubectl logs job/db-migrate
kubectl port-forward svc/backend 8000:8000 &
sleep 2; curl -s localhost:8000/ready; kill %1

Expect: The Job completes, its log says migrate: tables ready, and /ready now returns {"ready":true}.

Hint 1
A Job's pod needs restartPolicy: Never or OnFailure. Pick OnFailure and set backoffLimit to a small number.
Hint 2
It needs the same database settings as the backend: the ConfigMap plus DB_USER and DB_PASSWORD. The command is ["python", "tools.py", "migrate"].
Full solution
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migrate
  namespace: poll
spec:
  backoffLimit: 4
  template:
    metadata:
      labels: { app: backend-job }
    spec:
      restartPolicy: OnFailure
      containers:
        - name: migrate
          image: poll-backend:1.0
          command: ["python", "tools.py", "migrate"]
          envFrom:
            - configMapRef: { name: poll-config }
          env:
            - { name: DB_USER, valueFrom: { secretKeyRef: { name: db-credentials, key: username } } }
            - { name: DB_PASSWORD, valueFrom: { secretKeyRef: { name: db-credentials, key: password } } }
1.7

The frontend, two replicas

Run the frontend as a Deployment with 2 replicas. The container listens on 8080. The Service frontend exposes port 80 and forwards to 8080.

You write: k8s/50-frontend.yaml

Check

kubectl apply -f k8s/50-frontend.yaml
kubectl get pods -l app=frontend
kubectl port-forward svc/frontend 8081:80
# open http://localhost:8081 and vote

Expect: Two pods Running. The page loads, voting works and the totals change. The footer line shows the pod and node that answered.

Predict first: if you reload the page ten times, does the footer pod change?
No. kubectl port-forward picks one pod and keeps using it. You will see the replicas share traffic once you go through the Ingress in Act 2.
Hint 1
If the pod keeps restarting with host not found in upstream "backend", the backend Service does not exist yet. nginx resolves it when it starts.
Hint 2
targetPort can name the container port or use the number 8080.
Full solution
apiVersion: v1
kind: Service
metadata:
  name: frontend
  namespace: poll
  labels: { app: frontend }
spec:
  selector: { app: frontend }
  ports:
    - { name: http, port: 80, targetPort: http }
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
  namespace: poll
  labels: { app: frontend }
spec:
  replicas: 2
  selector:
    matchLabels: { app: frontend }
  template:
    metadata:
      labels: { app: frontend }
    spec:
      containers:
        - name: frontend
          image: poll-frontend:1.0
          ports:
            - { name: http, containerPort: 8080 }
