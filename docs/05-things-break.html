Troubleshooting
The second half

Act 5 · Things break

Kill a pod, the cache, the database and a whole node. Predict first, then watch the system recover or fail.

Story: the second half. Things start failing, one component at a time. For each failure, predict what the fans see, then break it and compare. Keep scripts/load.sh running in a second terminal for the first three missions.
5.1

A backend pod dies mid-match

Delete one backend pod while traffic flows, and count the failed requests.

Check

# terminal 2: scripts/load.sh http://localhost:8080 90 10
# terminal 1, while it runs:
for i in $(seq 1 300); do curl -s -o /dev/null -w '%{http_code}\n' localhost:8080/api/results; done | sort | uniq -c &
kubectl delete pod $(kubectl get pods -l app=backend -o name | head -1)
wait
kubectl get pods -l app=backend

Expect: A replacement pod appears within seconds. Almost all requests return 200; a few might fail with 502, the requests that were in flight to the pod that died.

Predict first: is any failed request acceptable, and what would reduce them?
A few in-flight failures are normal when a pod is killed abruptly. Graceful shutdown (handling SIGTERM and finishing requests), a preStop delay and client retries reduce them. Replicas make sure the service stays up; they do not make single requests immortal.
5.2

The cache disappears

Delete the Redis pod. Compare the totals and the source field before and after.

Check

curl -s localhost:8080/api/results
kubectl delete pod -l app=redis
curl -s localhost:8080/api/results
sleep 15
curl -s localhost:8080/api/results
kubectl get pods -l app=redis

Expect: The totals are identical each time. Right after the restart source is database (the backend rebuilt the cache from Postgres), and later cache again. The backend pods never leave Ready.

Predict first: are votes lost while Redis is down?
No. Votes are written to Postgres first. Redis only holds a copy of the totals, and the backend treats it as optional on purpose: /ready does not check it.
5.3

The database pod dies

Delete postgres-0 and compare the vote count before and after.

Check

kubectl exec postgres-0 -- psql -U poll -d poll -tc 'SELECT count(*) FROM votes'
kubectl delete pod postgres-0
kubectl get pods -w          # Ctrl+C when postgres-0 and the backends are Ready again
kubectl exec postgres-0 -- psql -U poll -d poll -tc 'SELECT count(*) FROM votes'

Expect: The same count after the restart. For about 20 to 40 seconds the backends turn 0/1 and the page shows errors, then everything recovers without a restart of the backends.

Predict first: why did the data survive, and why was the site down meanwhile?
The pod was recreated with the same name and re-attached to the same PersistentVolumeClaim, so the data stayed. The site was down because there is one database replica: a single replica of a stateful component is a single point of failure.
5.4

Drain a node for maintenance

Take a worker out of service the polite way. First find which worker hosts postgres-0 and drain the other one. Your PodDisruptionBudgets decide the pace.

Check

kubectl get pods -o wide
kubectl drain <the worker WITHOUT postgres-0> --ignore-daemonsets --delete-emptydir-data --timeout=180s
kubectl get pods -o wide
kubectl get nodes
curl -s -o /dev/null -w '%{http_code}\n' localhost:8080/api/results
kubectl uncordon <that worker>

Expect: The node shows SchedulingDisabled, and its pods move to the other worker. The drain may print Cannot evict pod as it would violate the pod's disruption budget and retry: that is the PDB working. The site keeps answering 200. After uncordon, nothing moves back by itself.

Hint 1
To rebalance after uncordoning: kubectl rollout restart deploy/backend deploy/frontend. The spread constraint places the new pods evenly again.
Hint 2
A drain cordons first and never uncordons. If it fails half way the node stays cordoned. Always check kubectl get nodes afterwards.
5.5

Stretch: drain the node that holds the database

Now drain the worker that hosts postgres-0. Predict what happens, then do it.

Check

kubectl drain <the worker WITH postgres-0> --ignore-daemonsets --delete-emptydir-data --timeout=60s
kubectl get pods -o wide
kubectl describe pod postgres-0 | tail -8
kubectl uncordon <that worker>

Expect: postgres-0 is evicted and then stays Pending. The events mention a volume node affinity conflict. After uncordon it starts again.

Predict first: why can't postgres-0 start on the other worker?
On kind the volume is a local folder on one specific node. The PersistentVolume carries a node affinity, so any pod using it must run on that node. With network-attached storage (a cloud disk) it could move; local storage ties the pod to its node.
