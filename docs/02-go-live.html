Match day, 18:00

Act 2 · Go live

Public access, health checks, resource sizing and placement. Four small changes that decide how the system behaves under stress.

Story: match day. The site is opened to the public. Make it reachable, make Kubernetes aware of what healthy means, and stop one node from holding everything.
2.1

Open the front door

Create an Ingress that sends all traffic for / to the frontend Service, using the nginx ingress class.

You write: k8s/60-ingress.yaml

Values to use

SettingValue
Ingress classingressClassName: nginx
Ruleno host, path /, type Prefix
BackendService frontend, port 80

Check

kubectl apply -f k8s/60-ingress.yaml
kubectl get ingress
curl -s localhost:8080/api/version
for i in 1 2 3 4 5 6; do curl -s localhost:8080/api/version | grep -o '"pod":"[^"]*"'; done

Expect: The poll opens at http://localhost:8080. The six calls show the backend pod names changing: the replicas share the traffic.

Predict first: why do different backend pods answer even though you always call the same URL?
Each browser or curl request creates a new connection through the frontend to the backend Service, and the Service picks a pod for each connection.
Hint 1
It is an networking.k8s.io/v1 Ingress with ingressClassName: nginx, one rule with no host, path / and type Prefix.
Full solution
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: poll
  namespace: poll
spec:
  ingressClassName: nginx
  rules:
    - http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend
                port:
                  number: 80
2.2

Teach Kubernetes what healthy means

Add readiness and liveness probes. Readiness controls whether a pod receives traffic. Liveness controls whether it is restarted. The backend's /ready already checks the database, and /health deliberately checks nothing.

You write: k8s/30-backend.yaml, k8s/50-frontend.yaml, k8s/10-postgres.yaml, k8s/20-redis.yaml

Values to use

ContainerProbeWhat to check
backendreadinessHTTP GET /ready on port http (8000), every 5 s, failureThreshold 2
backendlivenessHTTP GET /health on port http, initialDelaySeconds 5, every 10 s
frontendreadiness and livenessHTTP GET /healthz on port 8080
redisreadinessexec redis-cli ping
postgresreadinessexec pg_isready -U $POSTGRES_USER -d $POSTGRES_DB

Check

kubectl apply -f k8s/
kubectl get pods
# now break the database on purpose:
kubectl scale statefulset postgres --replicas=0
kubectl get pods -l app=backend -w      # watch for 20 seconds, then Ctrl+C
curl -s -o /dev/null -w '%{http_code}\n' localhost:8080/api/results
kubectl scale statefulset postgres --replicas=1

Expect: With Postgres gone the backend pods turn 0/1 within about 10 seconds but are not restarted. The site returns an error status. After you scale Postgres back, the pods turn Ready again by themselves.

Predict first: which probe fails when Postgres is down, and why must the other one not?
Readiness fails, so the pods are removed from the Service. If liveness also failed, Kubernetes would restart healthy pods in a loop for a problem restarting cannot fix.
Hint 1
Backend: readiness on /ready, liveness on /health, both on the named port http. Give liveness an initialDelaySeconds.
Hint 2
Frontend: both probes can use /healthz on port 8080. Redis: an exec probe with redis-cli ping. Postgres: an exec probe with pg_isready.
Full solution
          readinessProbe:
            httpGet: { path: /ready, port: http }
            periodSeconds: 5
            failureThreshold: 2
          livenessProbe:
            httpGet: { path: /health, port: http }
            initialDelaySeconds: 5
            periodSeconds: 10
          readinessProbe:
            httpGet: { path: /healthz, port: http }
            periodSeconds: 5
          livenessProbe:
            httpGet: { path: /healthz, port: http }
            initialDelaySeconds: 5
            periodSeconds: 10
          readinessProbe:
            exec: { command: ["redis-cli", "ping"] }
            periodSeconds: 5
          readinessProbe:
            exec:
              command: ["sh", "-c", "pg_isready -U \"$POSTGRES_USER\" -d \"$POSTGRES_DB\""]
            periodSeconds: 5
2.3

Requests and limits

Give every container resource requests, and a memory limit. Do not set CPU limits on the backend: you will autoscale on CPU use relative to the request, and a CPU limit would throttle it first.

You write: k8s/10-postgres.yaml, k8s/20-redis.yaml, k8s/30-backend.yaml, k8s/50-frontend.yaml

Values to use

ContainerCPU requestMemory requestMemory limit
backend100m128Mi256Mi
frontend20m32Mi64Mi
redis50m32Mi128Mi
postgres100m256Mi512Mi

Check

kubectl apply -f k8s/
kubectl get pods -o custom-columns=NAME:.metadata.name,QOS:.status.qosClass
kubectl describe node poll-worker | grep -A8 'Allocated resources'

Expect: Every pod is Burstable. The node description shows the sum of requests.

Predict first: which QoS class do these pods get?
Burstable: they have requests, but the limits differ from the requests and there is no CPU limit. Guaranteed would need requests equal to limits for CPU and memory.
Hint 1
Suggested sizes. Backend: 100m CPU / 128Mi, limit 256Mi memory. Frontend: 20m / 32Mi, limit 64Mi. Redis: 50m / 32Mi, limit 128Mi. Postgres: 100m / 256Mi, limit 512Mi.
Full solution
          resources:
            requests: { cpu: 100m, memory: 128Mi }
            limits: { memory: 256Mi }
2.4

Do not put all the pods on one node

Add a topology spread constraint to the backend and frontend so replicas spread across nodes. Use ScheduleAnyway so a lopsided cluster never leaves a pod Pending.

You write: k8s/30-backend.yaml, k8s/50-frontend.yaml

Check

kubectl apply -f k8s/
kubectl rollout restart deploy/backend deploy/frontend
kubectl rollout status deploy/backend
kubectl get pods -l 'app in (backend,frontend)' -o wide

Expect: The 3 backends sit 2 + 1 on the two workers, and the 2 frontends sit 1 + 1. No pod runs on the control-plane node, because it is tainted.

Hint 1
The constraint goes in the pod spec (next to containers), with topologyKey: kubernetes.io/hostname and a labelSelector that matches the pods' own app label.
Full solution
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: ScheduleAnyway
          labelSelector:
            matchLabels: { app: backend }
