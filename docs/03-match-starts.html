The first ball

Act 3 · Match starts

Generate load, let the HPA add replicas, and learn why changing a ConfigMap alone does nothing.

Story: the first ball is bowled. Votes arrive faster than three backend pods can handle. You need a way to generate that traffic, and a way for the cluster to answer it.
3.1

A fake crowd

Write a script that simulates voters: several parallel workers, each voting for a random team and then reading the results, for a number of seconds. Arguments: URL, duration, workers.

You write: scripts/load.sh

Check

chmod +x scripts/load.sh
scripts/load.sh http://localhost:8080 30 5
# watch the page at http://localhost:8080 while it runs

Expect: The totals on the page climb while the script runs, and the footer pod name keeps changing.

Hint 1
Each worker is a shell function run in the background (worker &) inside a loop; finish with wait. Bash has a built-in SECONDS counter you can compare with an end time.
Hint 2
A vote is curl -s -X POST -H 'Content-Type: application/json' -d '{"team":"India"}' URL/api/vote. $((RANDOM % 2)) gives 0 or 1.
Full solution
#!/usr/bin/env bash
# usage: scripts/load.sh [url] [seconds] [workers]
URL="${1:-http://localhost:8080}"
DURATION="${2:-60}"
WORKERS="${3:-10}"
end=$((SECONDS + DURATION))

worker() {
  while [ "$SECONDS" -lt "$end" ]; do
    if [ $((RANDOM % 2)) -eq 0 ]; then team="India"; else team="Australia"; fi
    curl -s -o /dev/null -X POST -H 'Content-Type: application/json' \
         -d "{\"team\":\"$team\"}" "$URL/api/vote"
    curl -s -o /dev/null "$URL/api/results"
  done
}

echo "load: $WORKERS workers for ${DURATION}s against $URL"
for _ in $(seq "$WORKERS"); do worker & done
wait
echo "load: done"
3.2

Let the cluster scale the backend

Create a HorizontalPodAutoscaler for the backend: between 3 and 8 replicas, aiming for 50% average CPU use relative to the request. Make it scale down after 60 seconds of calm instead of the default five minutes.

You write: k8s/70-hpa.yaml

Check

kubectl apply -f k8s/70-hpa.yaml
kubectl get hpa
# terminal 2: scripts/load.sh http://localhost:8080 150 30
kubectl get hpa -w
kubectl get pods -l app=backend

Expect: TARGETS rises above 50%, and REPLICAS grows from 3 towards 8 within a minute or two. When the load stops, REPLICAS falls back to 3 after about a minute.

Predict first: with 3 pods at 150% of their CPU request and a 50% target, how many replicas does the autoscaler want?
ceil(3 × 150 ÷ 50) = 9, capped at the maximum of 8.
Hint 1
The API is autoscaling/v2. The metric is type: Resource, name: cpu, target type Utilization.
Hint 2
Faster scale-down goes under behavior.scaleDown.stabilizationWindowSeconds. If TARGETS shows <unknown>, metrics-server is not working yet, or the pods have no CPU request.
Full solution
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: backend
  namespace: poll
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: backend
  minReplicas: 3
  maxReplicas: 8
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 60
3.3

Changing config does not restart pods

If the load does not trigger scaling on your machine, make each vote cost more CPU by raising CPU_COST_MS. Notice when the new value actually takes effect.

Check

kubectl patch configmap poll-config --type merge -p '{"data":{"CPU_COST_MS":"20"}}'
kubectl exec deploy/backend -- printenv CPU_COST_MS
kubectl rollout restart deploy/backend
kubectl rollout status deploy/backend
kubectl exec deploy/backend -- printenv CPU_COST_MS

Expect: The first printenv still prints 5. After the restart it prints 20. Update k8s/01-config.yaml too, or the next kubectl apply puts 5 back.

Predict first: why is the value still 5 after you changed the ConfigMap?
Environment variables are copied into the container when it starts. A running pod never re-reads them. Only mounted ConfigMap files update, and only the app can notice that.
Hint 1
Change the file as well as the live object. A patch edits only the cluster, so the file and the cluster now disagree.
3.4

See who does the work

While the load runs, look at CPU per pod and at where pods landed. This is how you confirm the replicas share the load and the autoscaler's new pods are placed sensibly.

Check

kubectl top pods -l app=backend
kubectl top nodes
kubectl get pods -l app=backend -o wide

Expect: CPU use is similar across the backend pods (the Service chooses pods roughly at random). New pods from the autoscaler are spread over the worker nodes.

Hint 1
kubectl top needs about a minute of data. Run it repeatedly with watch -n 2 if you have it.
